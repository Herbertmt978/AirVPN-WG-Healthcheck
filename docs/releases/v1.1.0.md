# AirVPN WireGuard Healthcheck v1.1.0

v1.1.0 keeps the original credential-free static workflow and adds an opt-in
API-managed workflow for unattended profile provisioning and rotation. The API path is
limited to one existing AirVPN device and preserves the installed WireGuard interface
identity.

## Highlights

- Choose static mode for an operator-owned profile or API-managed mode through
  `AIRVPN_PROFILE_SOURCE=api`.
- Use guided `wg-healthcheck-setup` flows to select countries, validate a fixed device,
  apply changes transactionally, and make an explicit timer decision.
- Recover managed profiles through strict parsing, identity pinning, durable journals,
  bounded retry state, and qBittorrent stop/start verification.
- Review managed recovery as bounded canonical source units while production admits one
  deterministically generated, fixed-path runtime module.
- Revalidate the managed module, provider executable, and their complete fixed-path
  ancestor chains before privileged loading or execution.
- Diagnose authenticated dry-run failures through a local, secret-free phase enum and,
  for response-contract failures, one of seven fixed local reason enums while preserving
  persistent backoff and failed-server exclusion.
- Request AirVPN's raw single-profile generator form explicitly through `format=text`
  while continuing to reject provider archives and every non-profile response before
  parsing or mutation.
- Install and operate the project under the MIT License with a dedicated
  [operator guide](../operations.md).

## Choose a mode

Static mode remains the credential-free default. It keeps the existing root-owned,
single-peer WireGuard profile and can optionally rotate only the public AirVPN endpoint.
No account key is opened and no authenticated request is made.

API-managed mode is an explicit opt-in for an existing fixed device. It can provision or
adopt a profile, refresh peer material, and select a healthy server, but it does not create,
renew, revoke, or delete an AirVPN device. Adoption succeeds only when the generated
private-key and IPv4 identity match the installed interface; mismatches fail closed.

The v1.1 provider boundary uses only public `status` data for selection, authenticated
`generator` output for the fixed device, and public `whatismyip` data for egress proof. It
does not call `userinfo`, `devices`, `disconnect`, `notification`, or `dns_lists`. AirVPN's
documented 600-requests-per-10-minutes ceiling is an outer provider limit; this release's
persistent request ledger is intentionally much stricter and must not be reset to force a
retry.

Provider profiles remain strictly hook-free. A validated root-owned installed profile may
retain ordered, repeated `PostUp` and `PostDown` commands during identity-pinned adoption
and rotation. They remain local root-executed `wg-quick` code and should be reviewed before
setup. `PreUp`, `PreDown`, `SaveConfig`, peer hooks, and unknown directives still fail
before profile mutation. API-managed adoption and rotation require the installed profile's
immediate directory (normally `/etc/wireguard`) to be a root-owned, non-symlinked directory
with exact mode `0700`; the profile remains a root-owned mode-`0600` regular file.

## Country selection

Before requesting a credential, setup reads the public status inventory and displays only
countries with an eligible healthy IPv4 WireGuard server. One country is strict; multiple
countries form a hard allowlist; their order is a soft preference because health, load,
and capacity select the final server. `ALL` must be an explicit sole-token choice and means
every currently eligible country. Blank or omitted API selection is rejected; runtime
stores accepted `ALL` as the canonical empty `AIRVPN_COUNTRIES` allowlist.

The shipped example allowlist is `GB NL BE DE IE`. It is a safe starting point rather than
a provider recommendation; setup displays the live eligible inventory so operators retain
control over the countries admitted by their own deployment.

## Upgrade and credential lifecycle

Verify the archive and `SHA256SUMS`, then use `sudo ./install.sh --quiesce <iface>` for a
live upgrade. Quiesce stops the selected timer and worker, waits for inactivity, checks
locks and recovery artifacts, installs the files, and leaves the timer disabled. It cannot
be combined with `--enable` or `DESTDIR`. Inspect `wg-healthcheck status`, run one manual
service check, and enable the timer only after a `healthy` or `recovered` result. A nonzero
or incomplete upgrade keeps automation disabled for recovery.

During a quiesced v1.0 upgrade, the installer can tighten only an unlocked, empty,
root-owned selected-interface legacy lock from mode `0644` to `0600`; every other unsafe
lock shape, owner, mode, link, interface, or non-quiesced attempt remains fail-closed.

API credentials are stored only at
`/etc/wireguard/healthcheck.d/<iface>.api-key`, beneath a root-owned mode-`0700`
directory as a root-owned mode-`0600` regular file. Interactive setup uses a hidden terminal
prompt; automation accepts only `--credential-file` with an absolute path to a root-owned
mode-`0600` regular file. Every parent component must be root-owned, non-symlinked, and
not writable by other users unless it is a root-owned sticky directory such as `/tmp`.
Replacement is explicit through `--replace-credential`; returning to static mode and removal
are explicit through `--remove-credential`, with `--restore-pre-managed` used only when the
saved profile should be restored. Ordinary uninstall preserves the credential and API state
for recovery.
Never put keys or generated profiles in arguments, environment variables, logs, tickets,
or chat.

## Limitations and known issues

- This software is not a firewall kill switch. Configure and test an independent policy
  that blocks non-VPN egress.
- Linux with systemd 249+, Bash 5.1+, Python 3.10+, and a single-peer WireGuard profile are
  required.
- API mode cannot change tunnel identity or manage device lifecycle. Missing, changed, or
  unsupported identity material blocks adoption.
- Provider authentication and device errors are persistently backed off; retries and
  failed-server exclusions are bounded rather than immediate or unlimited.
- Repeated `transport`, `response`, `profile`, or `internal` phases require operator
  investigation after the recorded backoff. A response phase may add only `status`,
  `encoding`, `media`, `read`, `size`, `json`, or `protocol`; these local enums contain no
  actual status, header, remote response detail, device identity, or profile material.
- Managed qBittorrent protection applies only to the explicitly configured container. If
  verified rollback is impossible, qBittorrent remains stopped.
- Static mode is never an automatic fallback for a failed API operation. VM migration and
  production-key acceptance require deployment-specific verification and are not asserted
  by these notes.
